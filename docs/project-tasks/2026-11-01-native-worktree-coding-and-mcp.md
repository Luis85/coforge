# Task: Let workflow agents implement and verify work in their own worktree

- Status: in progress
- Journey in `BRIEF.md`: request intake through an attributable increment for human review.

## Why

A dispatched coding agent needs its normal coding tools, native delegation and
project checks. Requiring a Docker recipe for ordinary implementation adds setup
without satisfying that workflow. External MCP agents need the same practical
task capabilities and actionable execution evidence.

## Traceability

- `design/traceability.json` contains no requirement entries for this increment.
- No generated `vi-*` obligation is claimed or edited.
- Owner decisions are recorded in `BRIEF.md`; this follows the CF-133 reliability
  and AI-cost increment in PR #65.

## Acceptance

- A newly admitted implementation-authorized editing step captures native or MCP
  worktree coding capability. An already admitted attempt retains its captured
  legacy access. Read-only and non-coding steps gain no shell or write authority.
- Native providers use the selected model, existing authentication, normal coding
  tools and provider-owned children in the attributed worktree. No Docker recipe,
  copied OAuth credential, administrative elevation or silent permission bypass
  is introduced. A worktree is described as Git organization, not OS isolation.
  Task instructions preserve the existing branch/HEAD invariant and leave edits
  uncommitted for host capture.
- MCP exposes task context, bounded file discovery/search/read, optimistic edits,
  patches/moves, commands, polling/cancellation, generated artifacts and captured
  diffs. Every effect rechecks the project, live task and owned workspace.
- Stable command keys prevent duplicate execution after uncertain responses.
  Command intent and private ownership precede effects. Public command/output
  evidence is bounded and sanitized; provider session observations do not become
  independently verified tests or human acceptance.
- Completion, cancellation, owner loss and recovery stop original command/SDK
  descendants before release. Missing lifetime proof preserves quarantine and
  evidence. Unavailable hosts fail explicitly instead of launching unowned work.
- Background attempts without a captured deadline remain uncapped. Explicit
  captured limits remain effective, and unavailable accounting is not invented.
- UI authoring and evidence clearly distinguish ordinary coding, MCP coding and
  captured legacy Docker verification. Human acceptance stays in Obsidian.

## Plan

   self-review, open the PR and merge only after required CI checks pass.

sign-in changes, administrative setup, and approval or final code acceptance by
an agent. Platform support requires independent lifetime qualification.
