CF-133Quality of life

Recruiting new CoWorkers

I want to have a "Hiring Pool" optino available at the CoWorkers page from where I can "hire" new CoWorkers. Those CoWorker are pre-defined agents which give me a starting point when I just have created a new environment or when adding a new project.

Implementation plan

This is the smallest useful version of CF-133 (Hiring Pool). The plugin will ship a small, read-only set of ready-made CoWorker templates in agent/v1 format. The CoWorkers page gets a "Hiring Pool" option, opened from the toolbar and from the empty state. Hiring a template works like Create CoWorker does today: createAgent() in src/plugin/presentation/composables/coforge/use-council-definitions.ts passes the definition through fresh(agentDefinitionCheck(...)). The hired copy gets a new agent-<uuid> ID, starts with enabled: false, provider demo and model sonnet, and opens as an unsaved draft in the existing editor. Nothing is written to the vault until the user presses the existing Save.

The following are left out of this version:

  • Bulk hire.
  • Provenance and "Hired" badges. These would need the origin field in the agent/v1 schema.
  • Vault-local templates.
  • Default-provider substitution.
  • The prompt after a project is created.
  • Template updates.

Because the schema stays the same, nothing changes in validation, persistence or the public data views. Hiring the same template twice simply makes two separate drafts with different IDs.

  1. Read src/plugin/features/coforge/domain/council-definitions.ts to confirm the exact agent/v1 type, the agentDefinitionCheck signature, its allowed provider and contextSources values, and any length limits on role and instructions. Templates must match this type exactly.

  2. Add a new domain module, src/plugin/features/coforge/domain/coworker-templates.ts. It exports a frozen COWORKER_TEMPLATES array of { templateId, category, summary, definition }, where definition is an agent/v1 body without id. Include 4–6 starters: Chat Moderator, Community Manager, Idea Board Triage, Product Scorer, Spec Writer and Stream Planner. Each has a name, a role and short plain-text instructions. All use enabled: false, provider: 'demo', model: 'sonnet', contextSources: [] and requestedCapabilities: { project: 'none', messaging: false }.

  3. In the same module, add a pure function hireCoWorkerTemplate(template, id). It returns agentDefinitionCheck({ schema: 'agent/v1', ...template.definition, id, enabled: false }), so a hired copy always starts disabled and is always validated.

  4. In src/plugin/presentation/composables/coforge/use-council-definitions.ts, add hireTemplate(templateId: string) next to createAgent(). It looks up the template, calls fresh(hireCoWorkerTemplate(t, agent-${crypto.randomUUID()})), and sets store.error if the ID is unknown. Add hireTemplate to the returned object near line 357.

  5. In src/plugin/presentation/composables/coforge/use-coworkers.ts, add a poolOpen ref and a poolSearch ref. Add a computed pool that filters COWORKER_TEMPLATES by name, role, summary and category. Add hire(id), which calls model.hireTemplate(id) and closes the pool. Return all of these from the reactive object.

  6. Create src/plugin/presentation/components/coforge/CoWorkerHiringPool.vue. It is a section with aria-label="Hiring Pool". It contains a search field, then a list of template cards; each card shows the name, role, summary and category, plus a <details> preview of the instructions. Each card has a cf-btn button labelled "Hire <name>", and the section has a Close button. Use CfIcon and the existing cf-coworker-card and cf-btn classes, and keep everything keyboard-accessible with real buttons.

  7. In src/plugin/presentation/components/coforge/CoWorkerInventory.vue, add a secondary "Hiring Pool" button next to Create CoWorker on line 14. It toggles inventory.poolOpen and is disabled while store.busy is true. Render <CoWorkerHiringPool> when the pool is open. In the empty state on line 34, when !inventory.total, add a "Browse the Hiring Pool" button.

  8. Add unit tests in src/plugin/tests/unit/coworker-templates.test.ts:

    • Every template passes agentDefinitionCheck.
    • templateIds and names are unique.
    • Every template has enabled === false and conservative capabilities.
    • hireCoWorkerTemplate keeps the given ID, forces enabled: false, and does not modify the source template.

  9. Extend src/plugin/tests/project/coforge/coworker-inventory-ui.test.ts, following its existing setup:

    • The empty inventory shows "Browse the Hiring Pool".
    • Opening the pool lists the templates.
    • Hiring one opens an editor draft with the template's name, role and instructions, with Disabled status, and causes no catalogue write before Save.
    • Hiring the same template twice gives two different IDs.
    • Search filters the pool.

  10. Update docs/components/views/coworkers.md (if it exists) with the actions "Hiring Pool" and "Hire" and the state "Pool open". Note that hired CoWorkers are unsaved and disabled until reviewed.

CF-134World

I want to save all of the stream chat messages

I want to ship SQLite with the plugin and have the possibilty to analyze and further inspect past chat messages.

Implementation plan

This first increment for CF-134 adds the storage contract and the capture pipeline for a chat archive, with no SQLite engine yet. It adds a ChatArchivePort, an in-memory adapter for tests, and a ChatArchiveRecorder. The recorder copies every committed chat message into the archive before prepareStudioCommit trims the live buffer to 250 messages. It also replays Twitch moderation removals (single message, user, clear chat) against the archive, so removed text is redacted there too, as the rule in chat-removal.ts requires. The archive is off by default.

The recorder follows the pattern in application/viewer-note-recorder.ts: it queues writes in batches, reports failures without blocking chat ingest, and flushes on dispose. The SQLite adapter (sql.js/WASM or better-sqlite3), the Studio "Chat history" view, retention and export are left for later increments, because the design draft's open questions Q1 (engine), Q2 (database location), Q3 (how to handle removed messages) and Q4 (which messages count as "all") need streamer answers first. Building the port now means the engine choice can be plugged in later without changing ingest. Files checked: application/chat.ts (ingestChat pushes the user message and an optional system:coforge reply inside store.transaction), application/chat-removal.ts (removeTwitchChat filters state.chat), infrastructure/coforge/runtime.ts (where the recorder would be wired) and infrastructure/coforge/twitch-module.ts (where removals arrive).

  1. Read src/plugin/features/coforge/application/studio-store.ts to find out whether StudioStore has a post-commit listener or subscribe API. Capture must run after the transaction commits, so rolled-back economy commands are never archived. It must also run before the 250-message trim in commit-policies.ts (prepareStudioCommit), or it must see the pre-trim message list. Record which mechanism you chose in the PR description.

  2. Create src/plugin/features/coforge/application/chat-archive-ports.ts with these types. ArchivedChatMessage: the ChatMessage fields plus removedAt?, with text nullable when redacted. ChatArchiveFilter: from?, to?, userId?, kind?, ideaId?, source?. ChatArchiveStorage: append(messages): Promise<void> (idempotent on id, and also on (source, externalId) when externalId is set), applyRemoval(removal: ChatRemoval): Promise<void>, query(filter, { limit, offset }): Promise<ArchivedChatMessage[]>, count(filter): Promise<number> and close(): Promise<void>.

  3. Create src/plugin/features/coforge/application/chat-archive-recorder.ts (ChatArchiveRecorder), modelled on ViewerNoteRecorder. It takes StudioStore, ChatArchiveStorage, Timers, a report() callback and an options object { enabled, includeSimulator=false, includeSystem=true }. It keeps a bounded set of already-archived chat ids and queues new messages. It flushes in batches of up to 200 through timers.setTimeout. If a write fails, the batch is put back in the queue and report() is called, and the error never reaches the ingest path. It exposes status() returning { pending, archived, failed } and an async dispose() that does a final bounded flush.

  4. Add recordRemoval(removal) to the recorder. It queues the removal in order after any pending appends, then calls storage.applyRemoval. Matching follows removeTwitchChat: by externalId for a single message, by twitch:${userId} for a user (only messages at or before removal.at), and every Twitch message at or before removal.at for clear chat. Only messages with the matching twitchChannelId are affected. Matching rows get text set to null and removedAt set.

  5. Create src/plugin/features/coforge/infrastructure/coforge/chat-archive-memory.ts (or put it under src/plugin/tests/project/coforge/ if test-only adapters live there, following memory-storage.ts). It is an in-memory ChatArchiveStorage that implements dedup, redaction, filtering, newest-first paging and count. A later SQLite adapter must pass the same contract tests.

  6. Wiring in src/plugin/infrastructure/coforge/runtime.ts: create the recorder next to ViewerNoteRecorder (around line 160) with the memory adapter for now, guarded by a setting flag that is off by default. Dispose it on unload. Leave a short TODO saying the SQLite adapter replaces the memory adapter in the next increment. Do not add any npm dependency in this increment.

  7. Wiring in src/plugin/infrastructure/coforge/twitch-module.ts (line 137, onRemoval): after removeTwitchChat resolves, call chatArchive.recordRemoval(input), with the same generation and closed guards as the existing call. Pass the recorder in through the module's existing constructor or dependency object. Do not change removeTwitchChat's signature.

  8. Add the setting flag (e.g. chatArchiveEnabled: false) where integration and community settings are defined and validated, which is likely domain/persisted.ts plus the settings defaults. Default it to false, so persisted state from earlier versions stays valid without a migration, or add a defaulting migration if the validator requires one. No UI toggle yet, unless a settings toggle is trivial to add with the existing pattern.

  9. Tests: create src/plugin/tests/project/coforge/chat-archive.test.ts, using the existing memory-storage.ts store helpers and the patterns in viewer-notes.test.ts and chat-removal.test.ts. Cover these cases. (a) Ingest 300 Twitch messages through ingestChat: the live state.chat stays capped at 250 and the archive holds all 300. (b) Replaying the same messageId adds no rows. (c) A failed economy command that triggers a rollback archives only the committed result. (d) Message, user and clear-chat removals each redact the matching archived rows, and a later replay of the removed message does not add the text back. (e) With the flag disabled, nothing is archived. (f) Simulator messages are excluded by default. (g) A storage append that throws calls report() and still lets ingestChat return a normal ChatResult. (h) dispose() flushes pending messages.
